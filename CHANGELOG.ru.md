## 0.3.17 (2026-09-13)

- **MSYS2 становится четвёртым бэкендом терминалов** (порядок в `SHELLS`: powershell / gitbash / msys2 / wsl). В `Config` добавлен `msys2Path`, подключённый через `resolveAllPaths`; `SHELL_DESCRIPTIONS.msys2` и `toolDescription` дополнены описанием бэкенда.
- **Настройка MSYS2 доведена до клиента**: строка «Терминал по умолчанию» в веб-UI раньше предлагала только powershell / gitbash / wsl — бэкенд MSYS2 существовал, но фронтенд не позволял его выбрать. `src/client.tsx` добавляет опцию `msys2` и двуязычные тексты `shell.msys2` (MSYS2 — имя собственное, в китайском и английском одинаково).
- **Исправление stdio-конвейера MSYS2**: `C:\msys64\msys2.exe` — это запускающий Cygwin-лаунчер, выделяющий консоль; при stdio через конвейер он возвращается с exit 0 и нулём байт (stdout/stderr по 0 байт, замерено на MSYS2 bash 5.3.15), и любая команда MSYS2 молча не давала вывода. Порядок кандидатов теперь: сначала `C:\msys64\usr\bin\bash.exe` → `bin\bash.exe` → записи mingw64/msys64 в PATH, а `msys2.exe` понижен до страховочного последнего пункта.
- **Login shell MSYS2**: `buildArgv` использует `-lc` вместо `-c`; только login shell выполняет source `/etc/profile`, добавляя `/usr/bin` и `/mingw64/bin` в PATH (при голом `-c` `bash` разрешается в `C:\Windows\System32\bash.exe`, и `gcc`/`make` оба дают command not found).
- **Окружение MSYS2**: `buildEnv` подставляет `MSYSTEM=MINGW64` (явно переданное пользователем значение имеет приоритет), чтобы gcc и make из `/mingw64/bin` попадали в PATH; env интерактивных сессий инструмента `terminal` согласован с этим поведением.
- **Песочница MSYS2**: как и Git Bash, без обёртки (restricted-token runner с Windows ACL несовместим с Cygwin/MSYS2); результат сообщает `enforcement: msys2-unconfined`.
- **Env интерактивного терминала идёт через `buildEnv`**: `src/terminal.ts` раньше собирал собственный env, минуя подстановку MSYSTEM из `buildEnv` — в итоге инструмент `shell` работал, а **интерактивный терминал** msys2 не получал `/mingw64/bin` (`/etc/profile` настраивал PATH под среду MSYS по умолчанию). Теперь: `buildEnv(shell, ctx.shellEnv.collect(exec), process.env.WSLENV)` — подстановка MSYSTEM получена, и логика WSLENV больше не дублируется. Третий параметр нужно передавать явно: `spawnTerminal` целиком заменяет окружение дочернего процесса через `childEnv(spec.env)`, иначе WSLENV из окружения остаётся невидимым.
- **WSL `WSLENV`: наращивание вместо пересборки**: WSLENV — это межмировой whitelist WSL; старый код пересобирал его только из `dshEnv`, теряя уже имевшиеся в окружении записи (локально `WSLENV=WT_SESSION:WT_PROFILE_ID:`, экспортирует Windows Terminal), и они больше не попадали в WSL. Теперь значения наращиваются поверх унаследованных: разбиение по `:` с фильтрацией пустых записей (унаследованное значение оканчивается на `:`, простая конкатенация строк порождала пустые записи), исключение самого ключа `WSLENV` (он тоже ключ `dshEnv`, добавление дало бы `...:WSLENV`); явно переданный вызывающим WSLENV приоритетнее унаследованных значений.
- **Интерактивный терминал**: `terminalArgv("msys2")` использует `-l`. Оставить `-lc` нельзя: этот argv не несёт команды (PTY сам является сессией), а `bash -lc` без операндов сразу завершается с `-c: option requires an argument` (exit 2).
- **Воспроизводимость клиентского bundle**: `scripts/build-client.mjs` раньше позволял esbuild искать tsconfig, поднимаясь вверх от `src/client.tsx`; сборка внутри репозитория находила корневой `tsconfig.json` и выдавала дополнительную строку `"use strict";`, а сборка worktree вне репозитория — нет — один и тот же исходник давал два разных закоммиченных артефакта. Теперь `tsconfigRaw: { compilerOptions: { target: "ES2022", useDefineForClassFields: true } }` зафиксирован явно (это реально действующие значения корневого tsconfig); единственное наблюдаемое отличие — исчезновение той самой строки `"use strict";`.
- **Защита от регрессий**: `test/unit.ts` проверяет `-lc`-argv msys2, подстановку `MSYSTEM` с приоритетом пользовательского значения, что `bash.exe` должен стоять раньше `msys2.exe`, и семантику наращивания `WSLENV` (унаследованные записи сохраняются / пустых записей нет / сам `WSLENV` не дописывается / явное значение приоритетно), плюс smoke-проверку реального spawn (stdout непуст и содержит `/mingw64/bin/gcc`; 0 байт = провал); `test/apply.ts` проверяет argv/env msys2, `msys2-unconfined` и структуру WSLENV; `test/terminal.ts` проверяет интерактивный argv и подключение PTY env через `buildEnv`, а также открывает **настоящую msys2-сессию через node-pty** (проверки `MSYSTEM=MINGW64`, `/mingw64/bin/gcc`, `BASH=/usr/bin/bash`); `test/client.ts` получает защиту от дрейфа — по каждому `SHELLS` хоста проверяется, что список клиентского bundle и отрендеренные пункты меню совпадают (включая порядок) и что в китайском и английском словарях есть `shell.<id>`. Каждая из этих защит проверена в обратную сторону (сломать артефакт сборки → проверка падает → после восстановления зелёная).

- Интерактивная проверка нескольких бэкендов: Git Bash (полностью), документированные ограничения ConPTY у PowerShell 5.1 и wsl.exe (0x8009001d / 0x8007072c; pwsh 7 и разовые -lc работают).
- README (zh/en): известные ограничения интерактивного терминала.

## 0.3.1 (2026-08-14)

- Терминальные сессии регистрируются в универсальном реестре задач (jobId при открытии; `job_kill` / `job_output` работают и на них).
- Таймаут простоя: сессии автоматически закрываются после 10 минут без send/read/signal (настраивается через `idleMs` при открытии), чтобы брошенные PTY не оставляли за собой деревья процессов.

## 0.3.0 (2026-08-14)

- **Инструмент интерактивного терминала (`terminal`)**: постоянные PTY-сессии через официальный стык `ctx.subprocess.spawnTerminal` (node-pty). Действия: `open` / `send` / `read` / `signal` (Ctrl+C и т.д.) / `close`. Состояние оболочки (cwd, переменные, алиасы) сохраняется между вызовами; бэкенд следует настройке терминала по умолчанию, выбранной пользователем. Проверено на настоящей интерактивной node-pty-сессии Git Bash (cd + pwd + echo + SIGINT + close).

## 0.2.1 (2026-08-14)

- **Официальная поверхность эскалации песочницы**: инструмент `shell` теперь объявляет `sandbox_permissions` / `justification` (точный контракт tool-bash / tool-pwsh): отклонённый вызов можно один раз повторить с самым узким из более широких режимов, маршрутизация через `ctx.approval` (`approveEscalation`), с строгой проверкой расширения полномочий.

## 0.2.0 (2026-08-14)

- **Интеграция песочницы (официальный стык)**: инструмент `shell` разрешает политику песочницы DSH при каждом вызове (`ctx.sandboxPolicy`) и оборачивает argv PowerShell / Git Bash через `ctx.sandbox` — та же fail-closed-семантика `SandboxUnavailableError`, что у штатных исполнителей. WSL работает без обёртки (его изоляция Linux-VM и ЕСТЬ песочница). Сведения песочницы (`sandbox.mode` / `sandbox.enforcement`) едут на результатах переднего плана.
- **Предпочтение модели**: раздел системного промпта плагина предписывает агентам предпочитать инструмент `shell`, а не `pwsh`, для терминальных команд; в описании инструмента первым указан выбранный пользователем терминал по умолчанию.

## 0.1.0 (2026-08-14)

Первый релиз.

- Инструмент `shell`: выполнять команды через PowerShell / Git Bash / WSL в Windows.
- Терминал по умолчанию выбирает пользователь в настройках веб-UI (Настройки → Общие → Терминал по умолчанию); модель не может его переопределить.
- Фоновое выполнение через универсальный реестр задач (`run_in_background` / `job_output` / `job_kill`).
- Клиентский плагин регистрирует строку настроек; хост-плагин читает настройку пользователя при каждом вызове.
- install.ps1: установка через junction, монтирование cordis.patch.yml и автоматический патч whitelist настроек dsh-host-apiproxy (ограничение DSH; см. README).
